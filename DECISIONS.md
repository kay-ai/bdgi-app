# Decisions

Where the build departs from `spec/` or DESIGN.md, or settles something they left open. Items marked **CONFIRM** need an answer from BGDI before launch.

## Engineering

**D-001 Embedded database for local work.** With `DATABASE_URL` empty the app uses PGlite (PostgreSQL compiled to WebAssembly) in `.data/pglite`. Spec/14 M0 asks for Docker Compose; PGlite removes that dependency for development and tests while running the same SQL and migrations. Staging and production use PostgreSQL through `DATABASE_URL`. Messaging inside a transaction takes the transaction's executor (`queueTemplate(..., tx)`) because PGlite has a single connection and would otherwise deadlock.

**D-002 Forms use React state and zod, not react-hook-form.** The forms are short and the same zod schemas validate on the server. Adding react-hook-form bought nothing.

**D-003 Offline intake sync calls the server action.** Spec/05 names `/api/sync/intake`. The Dexie queue replays the same `submitStudentAction` instead, so there is one code path and one validator. Idempotency is by the client-generated `clientId`.

**D-004 Redirects come from a static list in middleware.** Middleware runs before the database is reachable, so it reads the same list the seed writes to the `redirect` table. Console edits to redirects will need a deploy until the edge cache is wired (M5).

**D-005 Policy pages fall back to drafts in code.** `/privacy`, `/safeguarding`, `/terms` and `/cookies` render the drafts from spec/09 §8 (`src/content/legal.ts`) with a visible "draft" notice. Once BGDI publishes reviewed `content_page` rows, those replace the drafts. **CONFIRM:** review by BGDI and a lawyer; names of the safeguarding leads.

**D-006 Report-a-concern fields.** The form asks for category, what happened (at least 20 characters), whether anyone is in danger (yes / no / not sure), and optional name and contact with an "anonymous" switch. Spec/09 §2 also lists "who is this about", "school or place" and "when"; these are left to the free text for now to keep the form short. "Yes" to danger sets severity `emergency`.

**D-007 Story and event covers.** Media upload (S3) is not built yet. Covers stored as site paths (`/img/...`) render; anything else falls back to one of BGDI's own photographs.

**D-008 Partner enquiries reuse the contact form.** Spec/04 §6.9 lists an "interest" multi-select. The partner form stores the organisation in the message body with topic `partnership`; interests are left to the message text.

**D-009 Team cards show initials on gold** until BGDI supplies portraits (`team_member.photo_key`). The single leadership entry is shown as a row, not a large card, so no section is left mostly empty.

**D-010 Donations (M2).** `PAYMENTS_PROVIDER` picks the adapter (`src/server/providers/payments.ts`). `paystack` uses Paystack's hosted checkout, so card details never reach BGDI; the webhook (`/api/webhooks/paystack`) and the thank-you page (which asks Paystack's verify endpoint) both settle a gift through one idempotent update that only matches a donation still `initiated`, so replays and double visits change nothing and send nothing. A settlement whose amount or currency differs from the donation is not marked paid and is audited as `donation.amount_mismatch`. `console` (local and staging) settles at once; an amount ending in 13 (e.g. ₦513) fails, so the failure screen can be tried. A `sk_live_` key is refused unless `PAYSTACK_ALLOW_LIVE=true`. Departures from spec/11:
- **Receipts are rendered, not stored.** The PDF (`src/server/receipts/pdf.ts`, pdf-lib, one A4 page) is built from the donation row when the email is sent and when staff open it in the console, instead of a `receipt.generate` job writing a file. `receipt_key` stays empty until media storage (S3) exists. The standard PDF fonts only cover Latin-1, so the PDF writes "NGN 5,000.00" and drops Yorùbá underdots (ọ → o); **CONFIRM** whether BGDI wants an embedded font for full Yorùbá spelling.
- **The receipt email carries no name.** Message variables are stored in plain JSON beside the encrypted body, so the `donation.receipt` body has amount, date, designation, reference and receipt code only; the name is on the PDF.
- **Monthly renewals.** Paystack makes the reference for each renewal, so a `charge.success` with a plan and an unknown reference creates a new `paid` row for that supporter, copying designation and `subscription_code` from their latest monthly gift at the same amount. `subscription.create` writes the code onto the first gift. `invoice.payment_failed` creates one `failed` row per invoice (`BGDI-INV-…`) and sends `donation.failed`. `subscription.disable` is audited only (there is no subscription table). The first receipt says Paystack emails the manage link, because the subscription code arrives after the first charge.
- **USD** works end to end but stays off (`donations_usd_enabled`); **CONFIRM** that BGDI's Paystack account accepts USD before turning it on.
- **Fees** are stored from Paystack's `fees`; totals are gross.
- **CONFIRM** the CAC number and address (`org_cac_number`, `org_address`) so they print on receipts.

**D-012 Console access.** spec/14 built donations (M2) before sign-in (M3), so M2 closed the console outside development. Since M3 the console needs a full staff session (password and 2-step, D-013) and each console service checks `can()` itself: `donation.view` for programme managers and admins, `user.manage` for admins. `donation.manage` (resend, offline gift, refund) follows `donation.view` until spec/03 lists it. `CONSOLE_DEV_ACCESS` is gone. The console's own strings are English only; Yorùbá drafts cover the public and Hub pages.

**D-013 Sign-in built here, not Better Auth.** spec/01 names Better Auth; BGDI asked for no third-party auth library, so sign-in is our own code on Node's `crypto` (`src/lib/auth-crypto.ts`, `src/server/auth/`). What it does:
- **Sessions** are random 32-byte tokens in an httpOnly `bgdi_session` cookie; only the SHA-256 of the token is stored (`auth_session`), so a database leak gives no usable session. Phone and email sessions last 30 days, staff sessions 12 hours. Sign-out deletes the row.
- **Codes** (phone by SMS/WhatsApp, email for volunteers and champions) are 6 digits, stored as a keyed hash, valid 10 minutes, single use, 5 wrong tries, 5 requests an hour per number and 10 per IP. The answer is the same whether or not an account exists. Codes are never kept in message variables, and production logs never print message bodies.
- **Staff** sign in with email + password (scrypt) and then a TOTP code (RFC 6238, any authenticator app), or one of 10 single-use backup codes. Staff roles count only in a session that passed both steps; a code sign-in for a staff email sends nothing, and staff roles are stripped from any other session. Five wrong tries lock the account for 15 minutes and email the owner. Invites (72 hours) and resets (30 minutes) are emailed links. The first admin comes from `pnpm auth:invite-admin`.
- **Profiles.** One phone can be a guardian and their children; the person picked on `/sign-in/who` is the actor until they switch.
- **Not done yet:** passkeys, "sign out everywhere" for non-staff, and an admin reset of someone else's 2-step (today: deactivate and re-invite). **CONFIRM** that BGDI is happy without Better Auth's extras (social sign-in, magic links), which spec/03 does not ask for.

**D-014 Messaging core and consent follow-up (M4).** spec/08 §1–4 is in `src/server/services/messaging.ts`; consent reminders are in `consent-reminders.ts`.
- **Pipeline.** Every message is keyed by an event key, so a retried job never sends twice. Students who are not yet consented (or have declined, left or been anonymised) only get templates marked `allowBeforeConsent`. STOP is honoured except for sign-in codes, `staff.case_new` and `concern.received`, and the first `consent.request` still goes out. WhatsApp and SMS bodies (except sign-in codes) end with "Reply STOP to stop messages."
- **Quiet hours** (`quiet_hours`, default 21:00–07:00 WAT) hold WhatsApp and SMS until the morning; email and templates marked `ignoresQuietHours` go at once. Setting start equal to end turns them off.
- **Retries** at 1, 5 and 30 minutes, then WhatsApp falls back to SMS. If every channel fails the message is `failed`, and a failed `consent.*` or `session.*` message opens a staff task.
- **Links and codes are never stored.** Only hashes of the guardian's link and code are kept, and messages that carry them keep no variables. So each reminder sends a fresh link and code: the old link stops working, the five-try counter resets, and the 14-day expiry stays where it was.
- **Schedule.** Reminders on day 2 and day 6, a `consent_stalled` task on day 10, and the link expires on day 14. Staff can reissue it, which restarts the schedule and closes the stalled task.
- **Cron.** `vercel.json` runs `/api/cron/messages` daily at 07:05 WAT (to send what quiet hours held) and `/api/cron/consent-reminders` daily at 09:00 WAT. Both need `Authorization: Bearer $CRON_SECRET`. Most messages send straight after the change that caused them, so the daily job only catches retries and held messages. **CONFIRM** the Vercel plan: Hobby allows only daily crons, so retries can wait until the next morning; on Pro, run `/api/cron/messages` every 5 minutes.
- **Not done yet:** `consent.school_notice` (the school route) has no opt-out link yet.
- **Back to the page you asked for.** The middleware stamps the requested path in an `x-bgdi-path` request header (always overwritten, so a client cannot set it). The sign-in guards prefer it over the fallback a layout passes, and the 2-step and 2-step setup pages carry `next` through. Signing in from `/console/donations?tab=monthly` now lands back there, not on `/console`.

**D-025 Live group sessions and group chat (ahead of M6).** BGDI asked for coaches to meet their groups by video inside the app and to chat with them there.
- **Sessions.** Staff with `session.manage` create a group's weekly sessions from its meeting day, time and dates (`generateSessions`; dates already there are skipped), add one-off sessions and cancel planned ones with a reason. Coaches can add sessions for their own groups too, from the coach Hub: **Start one now** (adds a session for this minute and starts it) or **Schedule a session** (date, time, length). A coach can't add one in the past or to a finished group, and can't cancel; this uses `session.mark_held` (the right to run the group's sessions) so spec/03 needs no new action. Public holidays are not skipped automatically: staff cancel those one by one. Times are Lagos time (UTC+1).
- **Going live.** A coach of the group (or staff, `session.mark_held`) can start a session from 30 minutes before until 2 hours after its end. Starting opens a video room and sends `session.started` once to each student (her own email, else a guardian's), with a link to `/app/session/{id}`. While it is live the student Hub shows a pulsing gold "Join the session" button (the pulse stops for reduced motion) and the coach's Hub shows "Go back in". Coming in marks a student present; the coach can correct attendance (here, absent, excused). Ending marks the session held and logs the coach's volunteer hours from the time it was live (to the quarter hour, at least 15 minutes, at most the planned length). A session nobody ends is closed by the nightly `sessions` cron after 4 hours.
- **Video.** `VIDEO_PROVIDER` picks the service (`src/server/providers/video.ts`). `daily` (Daily.co, `DAILY_API_KEY`; 10,000 free minutes a month) makes a private room per session that expires after 4 hours, with a short-lived token per person, shown in the page with a **Full screen** button. On a phone (narrower than 768px) the page doesn't embed the call: an **Open the call** button opens it full screen in its own tab. The embedded box was too small on phones, and one phone participant couldn't hear the others while they could hear her, which points at the phone browser's rules for sound in an embedded frame. The session page's Permissions-Policy and the frame's `allow` also grant `speaker-selection`, `screen-wake-lock` and `compute-pressure`, as Daily's own embed does. `jitsi` (`JITSI_DOMAIN`) is ready for a self-hosted Jitsi server; that needs its own server with open UDP ports and can't run on Vercel. Empty means no video: the page says so and the session still works for attendance.
- **Chat.** Each group has one chat for its students and coaches. A coach and a student of the same group may also chat privately, which BGDI asked for. Safeguards: phone numbers, email addresses and links are refused; both people see a notice that staff can read the chat; safeguarding leads, admins and staff who manage the group read every chat read-only from the group's console page, and each opening is audited (`chat.view`); anyone can report a message, which hides it from the chat and opens a safeguarding case (category online, about the sender) for the leads. Messages are encrypted at rest. New messages arrive by the page asking every 4 seconds while it is open, so there is no extra service to run.
- **CONFIRM:** private coach–student chat goes against rules 2 and 3 of the volunteer code of conduct (spec/09 §8) as written. BGDI should update those rules to allow supervised in-app messages before this is used, or switch private chat off.
- **Not yet:** recording sessions, and push or email alerts for new chat messages (the Hub shows an unread count).

**D-026 Google sign-in and a year-long sign-in.** Users had to sign in too often, and BGDI asked for "Continue with Google" on the Hub sign-in page.
- **Google.** OpenID Connect with the code flow, PKCE, a state and a nonce (`src/server/auth/google.ts`, `/api/auth/google` and `/api/auth/google/callback`), with no extra package. Google only proves an email address; from there it is the same as an email code, so it reaches the person whose email matches (`openSession`). With no profile yet, the person goes to /join as today, so a new student or volunteer still fills in the join form. Staff can't use it: they keep password and 2-step. The button shows only when `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` are set. The redirect URI to register with Google is `{APP_URL}/api/auth/google/callback`.
- **Remembered for a year.** Hub sessions (code or Google) now last 365 days from the last visit, up from 30 days from sign-in. Each visit moves the end date on (`readSession`, at most once a minute), and the middleware renews the cookie on Hub pages only, so public pages stay cacheable. Staff sessions stay at 12 hours. Signing out still ends the session at once.

**D-015 The speech coach first, as a tailored lesson path.** BGDI asked for the Hub's debate and speech coach before M5/M6. spec/12 describes a scorecard; this build keeps all of spec/12 §1–3 and adds a path of lessons that adapts to each student.
- **Path.** Nine skills (`src/server/coach/curriculum.ts`): six about what you say (opening, structure, reasoning, evidence, rebuttal, closing) and three about how you say it (pace, smooth delivery, timekeeping). Each skill has a foundation and a stretch lesson. A lesson teaches one technique with a weak and a strong example, then the student speaks and that technique is judged. **CONFIRM** the lesson wording with BGDI's debate coaches.
- **Tailoring** (`tailor.ts`). The first two-minute speech rates every skill. After each speech a rating moves 40% toward the new score (50% for the skill being taught). The next lesson is the unpassed lesson of the weakest skill; ties go to the earlier skill. "Expert debater" needs an average of 4.2 with every skill at 3.5 or more. The scorer is told the student's weakest skills, and it rewrites one sentence the student actually said, the way a strong debater would say it.
- **Listening.** `TRANSCRIBE_PROVIDER=aws` uses Amazon Transcribe, as in spec/12, with recordings in S3 (`STORAGE_PROVIDER=s3`). `groq` uses Groq's Whisper for trying it without AWS; it gives no word confidence, so "clear words" is left out of the stars rather than guessed. `console` stands in locally with a fixed practice speech.
- **Scoring.** BGDI chose a Groq open-weight model over Bedrock: `AI_PROVIDER=groq`, `GROQ_MODEL` defaulting to `openai/gpt-oss-120b`, with a strict JSON schema. The answer is checked with zod; after one retry, fixed sentences are used and only delivery counts toward the stars. Pace, fillers, pauses and timing are computed in code (`metrics.ts`), never by the model. The prompt is versioned (`coach-v2` adds staff's rubric guidance from `/console/ai`).
- **Upload.** The recording is posted to `/api/speech`, at most 3 MB, rather than sent to S3 by presigned PUT. A 2½-minute speech at 32 kbps is about 600 KB, well inside Vercel's limit, and the server can check the type and size. Scoring runs after the response (`after()`); `/api/cron/speech` picks up any that were missed. The recording is deleted as soon as it has been heard, whatever the outcome.
- **Who can practise** (spec/12 §1): the kill switch `ai_enabled`; a student with `ai_practice` consent (or 18+ at sign-up); the monthly cap. Rejected or failed speeches don't count. BGDI decided the coach is mostly the AI listening and guiding each student on her own: her path and progress belong to her, not to a group, so there is no per-group switch and no setting for students not yet in a group (spec/12's per-cohort `ai_coach_enabled` is left in the schema, unused). A speech is filed under her current group only so her human coach can supervise it. **CONFIRM:** practice is open to students whose sign-up is `pending_review` as well as `active`.
- **Safety.** The transcript goes to the model as a JSON field and the prompt says to ignore instructions inside it. A safeguarding flag opens an `ai_flag` case and notifies leads; the student sees normal feedback. Transcripts are encrypted. Only the student can read their own attempt.
- **Offline.** A speech recorded with no connection is kept in IndexedDB (at most 3) and sent by itself when the phone is back online; the coach home lists what is waiting.
- **Read-aloud** (§6). "Listen to feedback" reads the encouragement, strengths and next steps. `TTS_PROVIDER=polly` uses Amazon Polly (`POLLY_VOICE`; the generative engine when the voice and region have it, else neural, else standard; `POLLY_ENGINE=neural` skips generative, which costs about twice as much), cached at `speech-tts/{id}.mp3`; the route streams the MP3 instead of returning a presigned URL, so it also works with local storage. Without Polly the phone's own voice reads it. The bucket's 1-day lifecycle rule should also cover `speech-tts/`.
- **History.** The coach home charts stars, pace and filler words over the last 12 scored speeches.
- **Staff and coaches** (§4, §5). Human coaches supervise; they do not coach the speeches themselves. A volunteer's home lists each of her groups' students with their own progress (rank, lessons passed, next lesson, recent stars and change, speeches this month) and flags who needs a look: never tried, can't practise, quiet for 14 days, low stars, stuck on a lesson, recording trouble, the AI fell back to fixed sentences, or a concern still open (`coach-supervision.ts`, `ATTENTION`). Her student page shows the path, the skill bars and the last 15 scorecards with the AI's feedback (no audio, no transcript), and she marks each scorecard "Looks right" or "Needs a look" with a reason (`coach_review`, migration 0005; notes encrypted). `/console/ai` (programme managers and admins): open concerns to resolve, kill switch, monthly cap, longest and shortest speech, rubric guidance, the pilot flag per cohort, this month's usage with an estimated cost (list prices in `coach-admin.ts`, `UNIT_COST`), the latest speeches, and motions (add, edit, stop using, import a list). Each cohort has an AI page (speeches per student, who hasn't tried). Staff see a student's speeches with transcripts and coaches' reviews at `/console/ai/student/[id]`, linked from the students list; every opening is audited (`speech.view_transcript`). These pages stand in for the cohort and person pages of spec/07 until M5 builds them.
- **WhatsApp** (§7). `/api/webhooks/whatsapp` takes Meta Cloud API messages (signed with `WHATSAPP_APP_SECRET`, voice notes downloaded with `WHATSAPP_TOKEN`): a message gets a motion (kept 24 hours in `bot_state`), a voice note becomes a `whatsapp` speech on that motion (or an open speech), NEW, SCORE and STOP work, and the scorecard comes back on WhatsApp. A guardian's phone works for an only child. It stays off until WhatsApp is set up, and replies go through the console adapter until a WhatsApp sender exists (M8). The "HELP ME" safeguarding route (spec/09) is not in it yet.
